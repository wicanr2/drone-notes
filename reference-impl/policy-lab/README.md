# policy-lab:飛行策略訓練骨架

這是 [65 章](../../docs/65-physical-ai-sim/)的程式版本。它**不是**要取代 Isaac Lab 或 Aerial Gym——那些是真正的訓練環境,這裡只有一個 200 行的平面四旋翼。

它要示範的是**外殼與驗收怎麼做**:

```
             ┌──────────────────────────────────────┐
   訓練環境  │ TrainEnv:窄參數範圍、無故障         │
   (窄)     └──────────────────┬───────────────────┘
                                │ 訓出策略
             ┌──────────────────▼───────────────────┐
   安全外殼  │ 觀測無效 → 安全預設                  │
             │ OOD      → 退回傳統控制器            │
             │ 輸出     → 限幅並計數                │
             └──────────────────┬───────────────────┘
                                │
             ┌──────────────────▼───────────────────┐
   驗收環境  │ EvalEnv:寬參數範圍 + 故障注入        │
   (寬)     │ 用指標斷言,不看 reward              │
             └──────────────────────────────────────┘
```

**把中間那個 200 行的模擬器換成 Isaac Lab,左右兩邊的結構完全不用改。** 這就是重點。

## 跑起來

```bash
cd reference-impl/policy-lab
docker run --rm -v "$PWD":/w -w /w ghcr.io/astral-sh/uv:python3.12-bookworm-slim \
  sh -c "uv venv -q && uv pip install -q -e '.[dev]' && .venv/bin/pytest -q"

# 訓練 + 驗收(約 64 萬步模擬,單執行緒 4~5 秒)
docker run --rm -v "$PWD":/w -w /w ghcr.io/astral-sh/uv:python3.12-bookworm-slim \
  sh -c ".venv/bin/python -m plab.train"

.venv/bin/python -m plab.train --eval-only   # 只跑退路控制器,當基準線
.venv/bin/python -m plab.train --ranges      # 印出訓練與驗收的隨機化範圍
```

純 numpy、單執行緒、無 GPU、確定性。整個訓練不到五秒——刻意做小,因為要示範的是結構不是算力。

## 實際跑出來的結果

以下是本機實測,不是預期值:

| 指標 | 退路 PD 基準 | 學出來的策略 | 門檻 |
|---|---|---|---|
| 墜毀率 | **0.000** ✓ | **1.000** ✗ | 0.00 |
| 位置誤差 p95 (m) | 1.595 ✓ | **1.557** ✓ | 2.00 |
| 最大傾角 (度) | **17.6** ✓ | **96.2** ✗ | 45.0 |
| 終端速度 (m/s) | **0.168** ✓ | 4.046 ✗ | 1.00 |
| 限幅率 | 0.000 ✓ | 0.138 ✓ | 0.30 |
| OOD 率 | 0.000 ✓ | 0.138 ✗ | 0.10 |

**學出來的策略在 reward 最在意的那個指標上贏了退路控制器(1.557 vs 1.595),但它 100% 墜毀。**

這正是 [65 章第 5 節](../../docs/65-physical-ai-sim/02-sim-to-real.md)那句「獎勵函數不是驗收標準」的實測版本。如果只看 reward 曲線或只看位置誤差,這個策略看起來是可用的。

### 為什麼退路控制器反而穩

因為它的增益不是調出來的,是用 [00 章](../../docs/00-system-overview/01-the-control-loop.md)那條 `φ = ω·τ` 算出來的:

```
驗收環境的最壞延遲 = 6 步 × 10 ms = 60 ms
願付出的相位落後   = 30° = 0.524 rad
→ 姿態迴路頻寬上限 ω ≤ 0.524 / 0.06 ≈ 8.7 rad/s
→ 取 ω_n = 6 rad/s 留餘裕
```

第一版沒照這條算,姿態取了 12 rad/s,在 60 ms 延遲下相位落後 41°,**退路控制器自己就會翻**(實測:墜毀率 8.3%、最大傾角 90.7°)。照公式重算之後,同一組驗收條件下墜毀率歸零、最大傾角降到 17.6°。

學出來的策略沒有「延遲預算」這個概念——它只擬合訓練時見過的延遲分布。驗收把延遲外推到 60 ms,它就垮了;而從物理約束推出來的控制器天生就撐得住外推。

**這是「先當規劃器、不要一開始就取代控制器」最直接的理由。**

## 想讓策略真的過關,要動什麼

這裡沒有做,列出來當練習(**未驗證**,不要當成保證有效):

- 獎勵函數加上傾角與角速度的懲罰,現在的權重(0.15)太輕
- 把延遲放進觀測,或給策略一段歷史,讓它能學到補償
- 換更大的策略(`LinearPolicy` 換成 MLP)與更多世代
- 用真正的 RL(PPO 之類)取代 CEM
- 訓練時也注入故障,現在只有驗收會注入

但**不要為了讓數字好看就放寬門檻**。門檻是從退路控制器的實測基準定的(見 `envs.py` 的 `GATES` 註解),放寬它等於把唯一抓到問題的機制關掉。

## 檔案

```
src/plab/
  dynamics.py    平面四旋翼,保留三個真實落差:馬達一階延遲、
                 感測到致動的延遲、姿態量測偏差
  randomize.py   隨機化範圍,寫成「參數辨識標稱值 ± 比例」;
                 EVAL 範圍每一項都比 TRAIN 寬
  policy.py      線性策略 + 三層安全外殼(無效觀測 / OOD / 限幅)
  envs.py        TrainEnv 與 EvalEnv 分開;驗收指標與門檻
  train.py       CEM 訓練與驗收進入點
tests/
  test_safety_shell.py   9 項,驗四條安全規則與「驗收範圍必須比訓練寬」
```

`test_safety_shell.py` 有兩項是寫測試才發現的真問題,程式已修:

**觀測是 NaN 時,降級到 fallback 也會輸出 NaN。** 「偵測到 OOD 就交給傳統控制器」漏掉了「傳統控制器也需要有效輸入」。現在無效觀測直接回安全預設值。

**tanh 已經把網路輸出夾在 ±1,外層的正規化限幅根本不會觸發。** 真正有意義的限幅要做在物理量上——PX4 的 `MC_NN_MAX_RPM` / `MC_NN_MIN_RPM` 就是這個形式。這裡保留正規化限幅,是因為它仍守得住沒有 squashing 的退路控制器輸出。

## 這個骨架沒有的東西

- **沒有真的 RL**。CEM 不是深度強化學習,只是能在五秒內跑完的最小可行替代。
- **沒有視覺**。觀測是六維狀態向量。
- **沒有三維**。平面模型,沒有偏航、沒有橫滾。
- **沒有接到飛控**。學出來的策略不會送進 PX4;真要做見 [65 章](../../docs/65-physical-ai-sim/02-sim-to-real.md)談的 `mc_nn_control` 路徑。
- **沒有 sim-to-real**。這裡的「real」也是模擬。

這些留白是刻意的。骨架要小到能一次讀完,而每一項都足以撐起自己的專案。
