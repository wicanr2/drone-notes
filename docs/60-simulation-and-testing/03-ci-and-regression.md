# 建一套自動化驗證系統

目標很簡單:**改了一行程式,五分鐘內知道有沒有弄壞任何東西。** 這在後端是基本要求,在無人機專案裡卻很少見——多數團隊仍然靠手動點地面站來驗證,結果是每次驗證成本高、覆蓋率低、而且不可重複。

這一章給一套可以照著建的結構。

---

## 1. 情境即程式碼

驗證的基本單位是**情境**:一組明確的初始狀態、要執行的任務、要注入的擾動,以及一組斷言。用宣告式的檔案描述,不要寫在測試程式的邏輯裡——因為情境會有幾十個,寫成程式碼很快就重複到難以維護。

```yaml
name: low-battery-triggers-rtl
vehicle: gz_x500
world: empty
mission: examples/survey-4points.json

inject:
  - at: 60s
    fault: battery_remaining
    value: 0.18

expect:
  events:
    - { event: failsafe.low_battery, within: 5s }
    - { event: mode_changed, to: RTL, within: 10s }
    - { event: landed, within: 180s }
  metrics:
    max_tilt_deg:            { max: 35 }
    landing_speed_mps:       { max: 1.5 }
    position_error_p95_m:    { max: 2.0 }
    cpu_load_max_pct:        { max: 85 }
```

這個格式的三個部分各有用意:

**`inject` 讓失效變成可重複的輸入。** 第 60 秒電量掉到 18%,每次都一樣。沒有故障注入,failsafe 這類路徑實質上無法測試。

**`expect.events` 是正向斷言。** [前面說過](01-what-simulation-proves.md),只斷言「沒崩」的測試沒有資訊量。要斷言預期的事情確實發生了,而且在預期的時間內。

**`expect.metrics` 擋的是「有完成但變差了」。** 這是最容易漏掉的一類回歸:任務照樣跑完,但追蹤誤差變成兩倍。沒有指標斷言,這種退化會一路累積到現場才被發現。

---

## 2. 該斷言哪些指標

從飛行紀錄算得出來、而且對回歸敏感的:

| 指標 | 抓什麼問題 |
|---|---|
| 位置誤差的 p95 與最大值 | 控制或估測退化 |
| 姿態追蹤誤差 | 內層控制退化 |
| 各軸的 innovation 統計 | 估測器健康度 |
| 最大傾角 | 控制過衝、參數不當 |
| 著陸接地速度 | 降落邏輯退化 |
| 任務總時間 | 效率退化或某段卡住 |
| 控制輸出的飽和比例 | 推力餘裕不足 |
| CPU 佔用最大值 | 即時性風險(SIH / 真機才有意義) |
| 各模式的停留時間 | 模式切換邏輯異常 |
| 掉包率與訊息速率 | 通訊設定退化 |

**門檻不要拍腦袋定。** 做法是先跑一批基準,取歷史分佈,把門檻設在「比目前最差還寬鬆一點」的位置,然後隨著系統改善逐步收緊。一開始就設得太嚴,團隊會學會忽略紅燈。

## 3. 故障注入矩陣

把[任務控制那章的失效矩陣](../40-mission-control/01-three-layers.md)直接翻成測試情境:

| 注入 | 預期行為 |
|---|---|
| 遙控器訊號中斷 | 依設定返航或降落 |
| 地面站鏈路中斷 | 任務續行 |
| GNSS 失效 | 降級到高度模式,不亂飛 |
| 電量降到門檻 | 返航;更低則就地降落 |
| 單一馬達推力下降 | 控制分配補償或安全降落 |
| 機載執行器行程被殺 | 飛控退出 Offboard,照航點骨幹續行 |
| 執行器重啟 | 從持久化狀態正確恢復 |
| 雲端連線中斷 | 事件緩衝,重連後補送且不重複 |
| 超出 geofence | 依設定行為,不越界 |
| 感測器資料凍結(值不再更新) | 偵測到並降級 |

最後一項特別值得測:**感測器「壞掉」不一定是資料消失,更常見的是資料停止更新但仍然存在。** 只檢查「有沒有資料」的程式碼會完全看不出來。

## 4. 執行架構

```mermaid
flowchart LR
    classDef ci fill:#E1F5FE,stroke:#0277BD,color:#01579B
    classDef run fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    classDef out fill:#FFF3E0,stroke:#EF6C00,color:#E65100

    TRIG["提交 / 排程"]:::ci
    MATRIX["情境矩陣<br/>N 個 YAML"]:::ci
    RUN["容器:PX4 SITL + Gazebo(無頭)<br/>+ 受測軟體 + 注入器"]:::run
    ASSERT["斷言器<br/>解析事件流與飛行紀錄"]:::run
    ART["產物:ULog · 事件流 · 指標 · 失敗時的軌跡圖"]:::out
    REP["報告:通過 / 失敗 / 指標趨勢"]:::out

    TRIG --> MATRIX --> RUN --> ASSERT --> ART --> REP
```

實作要點:

**一個情境一個容器,完全隔離。** 共用一個模擬器實例會讓失敗互相污染,而且無法平行。

**無頭執行。** 不要開圖形介面,不要開影像串流(除非那正是被測項目)。

**平行度由資源決定。** Gazebo 的 SITL 情境在一般 CI 節點可以同時跑數個。先量單一情境的 CPU 與記憶體,再決定平行度。

**失敗一定要留產物。** ULog、事件流、參數快照、以及一張軌跡圖。沒有這些,失敗的 CI 只是一個紅燈,沒人查得動。

**每個情境都要有硬性逾時。** 模擬會卡住,而卡住的情境會佔住資源不放。

---

## 5. 分層執行,控制成本

不是所有情境都值得每次提交跑:

| 觸發 | 跑什麼 | 目標時間 |
|---|---|---|
| 每次提交 | 核心 10~20 個情境:起降、任務執行、Offboard 進出、主要 failsafe | 5 分鐘內 |
| 合併到主線 | 完整矩陣含所有故障注入 | 30 分鐘內 |
| 每晚 | 完整矩陣 × 隨機化情境多次重複 | 數小時 |
| 每週 | Isaac Sim 的視覺情境、長時間任務、多機情境 | 不限 |
| 發版前 | SIH / HITL,補時序與 CPU 負載 | 人工參與 |

**五分鐘是關鍵門檻。** 超過這個時間,開發者就會在等待期間切換去做別的事,回饋迴路就斷了。核心情境要控制在這個範圍內,寧可覆蓋率低一點。

---

## 6. 處理不穩定的測試

模擬情境會有偶發失敗,原因可能是:模擬器啟動競態、隨機化的初始條件剛好踩到邊界、真的有偶發 bug。

處理原則:

**先分類再處理。** 記錄每個情境的失敗率。穩定失敗的是真 bug;偶發的要先判斷是基礎設施問題還是被測系統的問題。

**不要用重試掩蓋。** 加上「失敗自動重跑三次」很誘人,但它會把「十次有一次會摔機」變成綠燈。如果真的要重試,必須把重試次數記錄下來並監控趨勢。

**隨機化的種子要記錄。** 失敗時要能用同一個種子重現。無法重現的失敗等於無法修。

**基礎設施的失敗要跟被測系統的失敗分開統計。** 模擬器沒起來跟飛機摔了是完全不同的事,混在一起會讓失敗率失去意義。

## 7. 最小可行的第一步

如果從零開始,照這個順序建,每一步都能單獨產生價值:

1. **一個容器能無頭跑起 SITL,並在任務完成後正常退出。** 這一步最花時間,但之後所有東西都建在上面。
2. **一個情境:起飛 → 飛四個航點 → 降落,斷言「完成」。** 有了第一個綠燈。
3. **把 ULog 解析出來,加三個指標斷言。** 開始能擋住品質退化。
4. **加故障注入,做第一個 failsafe 情境。** 開始能驗證安全行為。
5. **把情境抽成 YAML,加到十個。** 開始有覆蓋率。
6. **接進 CI,設五分鐘的核心集合。** 回饋迴路建立。
7. **開始收集指標趨勢。** 從「有沒有壞」進步到「有沒有變差」。

多數團隊卡在第一步,因為把 SITL 跑進容器並讓它乾淨退出比想像中麻煩。這也是 [`reference-impl/`](../../reference-impl/) 存在的理由——那一步已經幫你做完了。

---

## 8. 這一章的結論

1. 情境用宣告式檔案描述,包含初始狀態、注入的故障與斷言,不要寫死在測試程式裡。
2. 斷言要有三層:任務完成、預期事件發生、品質指標在區間內。第三層擋的是「有完成但變差了」。
3. 指標門檻用歷史分佈定,一開始寬鬆再逐步收緊,免得團隊學會忽略紅燈。
4. 故障注入矩陣直接來自失效矩陣;特別要測「資料停止更新但仍存在」這種故障。
5. 一情境一容器、無頭、有硬逾時、失敗留完整產物。
6. 分層執行:核心集合控制在五分鐘內,完整矩陣放合併與夜間。
7. 不要用自動重試掩蓋不穩定;隨機種子要記錄,無法重現的失敗等於無法修。
