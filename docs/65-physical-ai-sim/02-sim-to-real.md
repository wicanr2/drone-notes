# 從訓練到上機:策略要放在哪一層

在模擬裡訓出一個能飛的策略,離「能上真機」還有兩個問題要回答:**模擬跟真實差在哪**,以及**這個策略要跑在系統的哪一層**。

第二個問題比第一個更常被忽略,但它其實有明確答案——用[第一章那張延遲預算表](../00-system-overview/01-the-control-loop.md)就能定案。策略輸出什麼,決定它只能跑在哪裡,而那又決定了它失效時系統還剩下什麼。

---

## 1. 缺口在哪裡

[60 章列過](../60-simulation-and-testing/01-what-simulation-proves.md)哪些東西模擬得準、哪些不準。訓練的情境下,幾個缺口特別致命,因為策略會**學會利用模擬器的缺陷**:

| 缺口 | 為什麼對訓練特別致命 |
|---|---|
| 致動器動態 | 模擬常把馬達當成瞬時響應;策略會學出真實馬達跟不上的高頻動作 |
| 迴路延遲 | 模擬裡感測到致動可能是零延遲;策略會依賴這個不存在的即時性 |
| 電池電壓下降 | 滿電與低電的推力上限差很多;只在滿電條件訓練,低電時策略失準 |
| 氣動擾動 | 地面效應、槳間干擾、機體擾流,模擬多半簡化 |
| 感測器偏差 | 模擬的 IMU 太乾淨,策略沒學過偏差漂移 |
| 質量與慣量 | 真機組裝的差異、掛不同酬載,都跟模型不同 |

**策略「鑽模擬器漏洞」是真實現象**,而且它在模擬裡的表現會非常好看——因為它找到的正是模擬器的錯處。獎勵曲線漂亮不代表能飛。

---

## 2. Domain randomization:要隨機什麼

處理缺口的主要手段是把不確定性訓進去。對多旋翼,值得隨機的項目與大致範圍:

| 項目 | 為什麼 |
|---|---|
| 質量、慣量張量 | 涵蓋組裝差異與不同酬載 |
| 推力係數、馬達時間常數 | 涵蓋槳與馬達的批次差異、老化 |
| 感測到致動的延遲 | 這一項最重要,而且最常被漏掉 |
| IMU 雜訊與偏差漂移 | 讓估測不再完美 |
| 風:穩態 + 陣風 | 對照[機體的抗風上限](../15-airframes-and-envelope/02-trajectory-and-planning.md) |
| 電池電壓曲線 | 讓策略在推力餘裕變小時仍可用 |
| 視覺任務:光照、材質、相機參數 | 涵蓋不同天候與時段 |

一條實用的原則:**隨機的範圍要涵蓋真實值,而且要略微超過。** 如果真機的延遲是 8~15 ms,訓練時就隨機 5~25 ms。範圍太窄等於沒隨機,太寬則策略會保守到不可用——這個上下界要靠真機量測來定,不是拍腦袋。

這也說明了為什麼[參數辨識](../15-airframes-and-envelope/01-platform-parameters.md)值得先做:你得先知道真機的參數落在哪,才知道要隨機在哪個區間附近。

---

## 3. 策略要放在哪一層

這是整章最重要的一節。策略輸出的東西決定它的更新率需求,更新率決定它能放哪:

| 策略輸出 | 更新率 | 能放在 | 失效時系統還剩什麼 |
|---|---|---|---|
| 航點 / 路徑 | 1~10 Hz | 伴隨電腦 | 飛控照既有航點續飛,幾乎無風險 |
| 速度 / 位置 setpoint | 10~50 Hz | 伴隨電腦(Offboard) | 飛控退出 Offboard,回安全模式 |
| 姿態 / 角速率 setpoint | 50~250 Hz | 伴隨電腦勉強,飛控較穩 | 退出外部控制,但已接近邊界 |
| **直接馬達指令** | 500~1000 Hz | **只能在飛控上** | **沒有安全網,策略就是最後一層** |

前兩列是絕大多數應用該待的地方:**策略當「更好的規劃器」,而不是「取代控制器」。** 這樣做的好處是失效行為已經被前面幾章的設計涵蓋了——策略掛掉就是 Offboard 掉線,飛控接手,而那條路徑你已經測過。

最後一列則是完全不同的處境。要在 1 kHz 上跑推論,只能跑在飛控的 MCU 上,而且一旦策略輸出異常,**它下面沒有任何東西可以擋。**

## 4. PX4 主線裡的低階部署路徑

值得注意的是,這條「最激進的路」現在在 PX4 主線裡是有實作的。`src/modules/mc_nn_control/` 這個模組,原始碼註解寫得很直接:

> Multicopter Neural Network Control module, from position setpoints to control allocator.

也就是說,它用一個網路取代了**從位置 setpoint 一路到控制分配之間的整條串級**——[10 章那張資料流圖](../10-flight-controller/02-estimation-and-control.md)裡的位置、速度、姿態、角速率四層,全部換成一次推論。

模組包含 `control_net.cpp` / `control_net.hpp`(網路本體)與一組參數:

| 參數 | 大致作用 |
|---|---|
| `MC_NN_EN` | 啟用開關 |
| `MC_NN_MAX_RPM` / `MC_NN_MIN_RPM` | 輸出轉速的上下限 |
| `MC_NN_THRST_COEF` | 推力係數 |
| `MC_NN_MANL_CTRL` | 與手動控制相關的行為 |

(參數的精確語意以韌體內的參數說明為準。)

有兩件事值得從這個模組讀出來:

**它有開關與限幅,不是全有全無。** `MC_NN_EN` 讓你能退回傳統控制器,`MC_NN_MAX_RPM` / `MIN_RPM` 把輸出鎖在物理合理範圍內。這正是把學習元件放進安全關鍵路徑時該有的設計——**不要讓網路的輸出直接就是最終命令。**

**訓練與部署的閉環已經在同一個生態裡。** 模組作者之一署名 NTNU,而[上一章](01-training-stack.md)提到的 Aerial Gym Simulator 出自 NTNU 的自主機器人實驗室。訓練環境與韌體側的部署路徑來自同一群人,這對想走這條路的人是好消息——但也要理解它仍是相對新的東西,不是成熟到可以照抄的產線方案。

---

## 5. 把學習元件放進安全路徑的四條規則

**一、輸出一定要限幅,而且限幅要在網路外面。** 網路輸出過限就截斷,並記錄下來。截斷次數本身就是一個健康指標——常截斷代表策略正在遇到它不熟的狀況。

**二、要有能一鍵回去的傳統控制器。** 而且切換不能需要重開機。這跟 [`px4-ros2-interface-lib` 的 fallback 機制](../10-flight-controller/03-extending-and-testing.md)是同一個思路:學習元件失效時,退回一個你完全理解的東西。

**三、要監控輸入是否落在訓練分布內。** 神經網路的失效模式跟傳統控制器不一樣:傳統控制器在極端輸入下通常是「表現變差」,網路則可能是「輸出完全無意義」。所以要在執行期檢查觀測值是否超出訓練時見過的範圍,超出就降級。

**四、獎勵函數不是驗收標準。** 訓練用的 reward 跟系統該滿足的性質是兩回事。驗收要用[60 章那組指標](../60-simulation-and-testing/03-ci-and-regression.md):追蹤誤差、最大傾角、著陸速度、控制輸出飽和比例。

---

## 6. 驗收:訓練環境不能當驗證環境

這是最容易犯、後果也最尷尬的錯:在訓練環境裡測策略,結果很好,上真機就爛。

原因很單純——策略見過那個環境。要驗證泛化,至少要換掉這幾樣:

- **不同的隨機種子與初始條件**(最低限度)
- **不同的參數範圍**,包含訓練時沒涵蓋的邊界
- **不同的模擬器**,如果做得到。在 Isaac 系訓練、拿 Gazebo 驗證,能抓到不少對特定引擎的過擬合
- **[60 章的故障注入矩陣](../60-simulation-and-testing/03-ci-and-regression.md)**

最後一項要特別強調。**學出來的策略在故障情境下的行為是全新的未知**——它訓練時可能從來沒遇過 GNSS 失效或單顆馬達推力下降。傳統控制器在這些情況下的行為是可以分析的;網路不行,只能測。

---

## 7. 一條務實的路線

如果目標是「建一套能真的用的 Physical AI 模擬環境」,這個順序每一步都能單獨產生價值:

| 步驟 | 做什麼 | 完成的標準 |
|---|---|---|
| 1 | 先建好[驗證環境](../60-simulation-and-testing/03-ci-and-regression.md) | SITL 情境測試能在 CI 跑 |
| 2 | 真機參數辨識 | 質量、慣量、推力係數、延遲有量測值 |
| 3 | 選一套學習環境跑通 | 訓出一個能在模擬裡懸停的策略 |
| 4 | 加 domain randomization | 策略在參數擾動下仍可用 |
| 5 | 換環境驗證 | 在**沒訓練過的**條件與故障注入下通過指標斷言 |
| 6 | 部署在最高的可行層級 | 先當規劃器,不要一開始就取代控制器 |
| 7 | 繫留與 HITL | 量到真實的時序與 CPU 佔用 |
| 8 | 實飛,保留一鍵退回 | 傳統控制器隨時能接手 |

第一步排在最前面不是形式:**沒有驗證環境,你沒有辦法判斷訓出來的策略是好是壞**,而這件事在訓練開始之後才發現會非常痛。

第六步的「先當規劃器」也值得堅持。把策略放在航點或速度層,失效行為是已知的;直接跳到馬達層,你同時要處理「策略對不對」與「安全網不見了」兩個問題。

---

## 8. 這一章的結論

1. 訓練的缺口比驗證更致命,因為策略會學會利用模擬器的缺陷,而且在模擬裡表現會很好看。
2. Domain randomization 的範圍要涵蓋真實值並略微超過,而上下界要靠真機參數辨識來定。
3. 策略輸出什麼決定它能放哪一層:航點與速度層失效有安全網,馬達層沒有。
4. PX4 主線的 `mc_nn_control` 用一個網路取代整條串級,而且帶開關與輸出限幅——學習元件不該直接就是最終命令。
5. 四條安全規則:外部限幅、可一鍵回退、監控分布外輸入、獎勵不是驗收標準。
6. 訓練環境不能當驗證環境;換種子、換參數範圍、換模擬器、跑故障注入,尤其因為策略在故障下的行為是全新的未知。
7. 路線從驗證環境與參數辨識開始,部署時先當規劃器再談取代控制器。
