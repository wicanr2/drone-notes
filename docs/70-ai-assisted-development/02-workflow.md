# 工作流:先建迴路,再談產出

這一章給一套可以照著做的流程,以及一個完整的走查:用 AI 工具在機載任務執行器裡加一個新動作,從契約寫到測試通過。

核心原則只有一條:**在這個領域,產出程式碼從來不是瓶頸,驗證才是。** 所以整套流程都繞著「怎麼讓驗證變便宜」設計。

---

## 1. 順序:回饋迴路排在第一位

```
1. 建可自動執行的 SITL 情境測試      ← 沒有這個,後面全部無效
2. 定義契約(介面、資料格式、斷言)
3. 產出實作
4. 跑情境,看斷言
5. 人工檢查安全相關的部分
6. 加指標斷言,防止之後退化
```

第一步的成本大約是一到兩天(容器化 SITL、無頭執行、解析飛行紀錄、一個能通過的情境)。這個投資在第三天就會回本,因為之後每一次驗證從「開模擬器手動點」變成「跑一個指令」。

**跳過第一步直接進第三步,是這個領域用 AI 工具最常見的失敗方式。** 產出速度變快了,但每一份產出都要人工開模擬器驗證,瓶頸從「寫程式」移到「驗證」,總時間沒有變短,而且累積了一堆沒被真正驗過的程式碼。

---

## 2. 走查:加一個「環繞目標拍照」的動作

需求:巡檢電線桿時,飛機要繞著目標飛一圈,每 45 度拍一張照,共八張。

### 步驟一:先寫情境,不寫實作

```yaml
name: orbit-photo-around-target
vehicle: gz_x500_gimbal
world: pole_inspection
mission: examples/orbit-photo.json

expect:
  events:
    - { event: action_started, action: orbit_photo, within: 60s }
    - { event: photo_captured, count: 8, within: 120s }
    - { event: action_completed, action: orbit_photo }
  metrics:
    orbit_radius_error_p95_m: { max: 1.0 }
    gimbal_pointing_error_p95_deg: { max: 5.0 }
    max_tilt_deg: { max: 30 }
```

寫測試比寫實作先,在這裡不只是紀律問題:**它逼你把「做完了」的定義講清楚。** 八張照片、半徑誤差、雲台指向誤差——這些是驗收標準,也是給 AI 的規格。含糊的需求會得到含糊的實作。

### 步驟二:定義契約

沿用[機載執行器那章](../40-mission-control/02-onboard-executor.md)的動作介面,把這個動作的具體行為寫清楚:

```
OrbitPhotoAction:
  參數:目標座標、半徑、高度、張數、每張之間的穩定等待時間
  preconditions:電量足夠繞完一圈 + 返航;雲台就緒;位置估計有效
  execute:切 Offboard;沿圓周移動;每 45° 停下,對準目標,拍照,確認存檔
  is_complete:已拍張數 == 目標張數,且每張都有確認存檔
  on_abort:停止移動,雲台歸位,退出 Offboard,回報已完成張數
  resume_policy:RESTART(照片要成組,中斷後重來)
```

`resume_policy` 選 RESTART 的理由要寫下來:八張照片是要拼成一組環景的,少了中間幾張這組資料就沒用,所以中斷後整組重來比續拍有意義。**這種決策要人來做,因為它牽涉業務語意。**

### 步驟三:產出實作

給 AI 的脈絡裡要有:動作介面的定義、專案已有的類似動作、[CONTEXT.md](../../CONTEXT.md) 的版本現況、以及情境 YAML。

同時要求它:

- **列出用到的每個外部 API 與參數,附出處**(哪個檔案、哪份文件)
- **不確定的地方明確標出來**,不要猜一個看起來合理的名字
- **中止路徑要跟正常路徑一樣完整**

第一項是最有效的一招。要求附出處之後,編造的 API 名稱會露餡——因為它給不出檔案路徑。

### 步驟四:跑情境

第一次跑通常會失敗,而失敗訊息本身就是回饋。常見的幾種:

| 失敗 | 通常代表 |
|---|---|
| 進不了 Offboard | setpoint 的預熱或頻率不對 |
| 繞了但半徑誤差大 | 速度與半徑的關係算錯,或沒有考慮風 |
| 拍到六張就結束 | 完成判定看送出的指令而非存檔確認 |
| 雲台指向誤差大 | 座標系或角度單位錯 |
| 中止測試卡住 | `on_abort` 裡有會阻塞的呼叫 |

這些都是模擬能抓到的,而且抓到時的訊息足夠具體。**這就是回饋迴路的價值:錯誤變成可讀的訊息,而不是「飛起來怪怪的」。**

### 步驟五:人工檢查安全相關的部分

情境通過不代表可以上真機。要人工看過的:

- **中止路徑**:所有 `on_abort` 裡的呼叫都不會阻塞、不會拋例外嗎?
- **逾時**:每個等待都有上限嗎?雲台不回應時會卡多久?
- **與 failsafe 的互動**:電量在繞圈中途掉到門檻,行為是什麼?
- **邊界值**:半徑設成 0 或 1000 公尺會怎樣?張數設成 0 呢?
- **資源**:八張 20 MB 的照片寫入時,會不會影響 setpoint 的送出頻率?

最後一項是這個領域特有的:**一個看起來無害的檔案寫入,可能讓 Offboard 掉線。** 這種跨層的影響是 AI 最不容易察覺的,因為它需要同時理解業務邏輯與即時性約束。

### 步驟六:加指標斷言

情境通過後,把當次的實際指標記下來,設成稍微寬鬆的門檻。之後任何人改動這塊,退化就會被擋住。

## 3. 專案裡該放什麼常駐脈絡

AI 工具的產出品質很大一部分取決於它拿到什麼脈絡。無人機專案值得常駐的:

| 內容 | 為什麼 |
|---|---|
| 版本現況(附查證日期) | 擋掉版本混用,這是最大的錯誤來源 |
| 座標系與單位的約定 | 擋掉方向與單位錯誤 |
| 三層責任邊界 | 擋掉「把業務邏輯寫進飛控」這類架構錯誤 |
| 動作介面與既有動作清單 | 讓新產出跟現有結構一致 |
| 情境測試怎麼跑 | 讓它能自己驗證 |
| 明確的紅線清單 | 「不要動控制參數」「不要改 failsafe 門檻」 |
| 官方原始碼在本機的路徑 | 讓它讀而不是憑記憶 |

這個 repo 的 [CLAUDE.md](../../CLAUDE.md) 就是這種檔案的例子——寫作規則、圖的分界、每篇的驗收標準、不臆造的要求都在裡面。同樣的做法可以直接套到程式專案上。

---

## 4. 讓工具讀原始碼

最實際的一招:把 PX4、px4_msgs、MAVLink 定義檔拉到本機或工作區,讓工具直接讀。

```bash
git clone --depth 1 --branch v1.17.0 https://github.com/PX4/PX4-Autopilot.git
git clone --depth 1 https://github.com/mavlink/mavlink.git
```

差別在於:讀原始碼的回答會說「這個參數定義在 `src/modules/mc_pos_control/module.yaml` 第 N 行」,憑記憶的回答只會給你一個名字。前者可以驗證,後者不行。

同樣的做法適用於除錯:把飛行紀錄轉成文字或表格餵進去,比描述症狀有效得多。**在這個領域,證據永遠比描述有價值。**

---

## 5. 幾個明確有效的用法

除了寫程式,這幾件事的投報率特別高:

**飛行紀錄分析。** 上百個欄位的時間序列,寫查詢腳本很瑣碎、邏輯很單純。「找出所有模式切換點並列出前後五秒的姿態誤差」這種需求,幾分鐘就有結果。

**情境產生。** 從失效矩陣批次產出情境 YAML,人工審一遍。這是純粹的樣板工作。

**跨版本差異比對。** 「這個模組從 v1.14 到 v1.17 改了什麼、對我們的整合有什麼影響」,讓它讀兩個版本的原始碼比對。

**文件與知識整理。** 把散落在 issue、討論串、原始碼註解裡的資訊整理成一份可讀的說明。

**程式碼審查的第一遍。** 特別是檢查「有沒有漏掉錯誤處理」「這個等待有沒有逾時」這類機械性的檢查。

## 6. 反模式

| 反模式 | 問題 |
|---|---|
| 還沒有 SITL 情境就開始大量產出 | 累積無法驗證的程式碼,瓶頸只是從寫移到驗 |
| 讓它憑記憶給參數名與 API | 幻覺率高,而且錯誤很晚才發現 |
| 用它調控制參數 | 紅區。它看不到你的飛行紀錄與機架特性 |
| 產出通過模擬就直接上真機 | 模擬驗不了時序、振動、磁干擾 |
| 一次要求它改一大片 | 失敗時無法定位是哪一處的問題 |
| 不記錄它用了哪個版本的知識 | 幾個月後沒人知道這段程式碼是照哪版寫的 |
| 把安全檢查也交出去 | 安全檢查的價值來自獨立性,同一個來源寫的檢查擋不住同一個來源的錯誤 |

最後一項值得展開。讓 AI 同時寫實作與測試,測試會傾向於驗證「它以為的行為」,而不是「應該的行為」。安全相關的斷言應該由人來定義,或至少由人逐條審過——**這是驗收的獨立性問題,跟工具好不好無關。**

---

## 7. 這一章的結論

1. 順序是:先建可自動執行的 SITL 情境測試,再產出程式碼。跳過第一步等於把瓶頸從寫移到驗。
2. 先寫情境再寫實作,因為它逼你把「做完了」的定義講清楚,而那份定義就是給 AI 的規格。
3. 要求列出每個外部 API 的出處,編造的名稱會因為給不出檔案路徑而露餡。
4. 情境通過不等於可以上真機;中止路徑、逾時、failsafe 互動、跨層資源影響要人工檢查。
5. 常駐脈絡至少要有:版本現況與查證日期、座標與單位約定、責任邊界、紅線清單、原始碼路徑。
6. 讓工具讀原始碼與飛行紀錄,而不是憑記憶回答;證據比描述有價值。
7. 安全相關的斷言要由人定義或逐條審過,因為驗收需要獨立性。
