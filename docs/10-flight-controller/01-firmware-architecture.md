# 飛控韌體的軟體架構:在 1 MB RAM 上跑硬即時系統

飛控韌體的每一個架構決策,都是同一組約束逼出來的:**一顆兩百多 MHz、記憶體以 MB 計的 MCU,要同時餵飽二十幾個感測器、五六條通訊鏈路,還要保證某一段程式碼每毫秒準時執行一次,而且不能當機。**

寫過後端的人看到 PX4 的原始碼,常會覺得「為什麼要搞得這麼複雜,不就是讀感測器算一算輸出嗎」。這一章就是回答那個為什麼。看懂之後你會發現,它用的都是你熟悉的模式——發佈訂閱、事件溯源、依賴注入、優先權佇列——只是在極端資源限制下的版本。

以下以 PX4 為例(原始碼結構取自 main 分支),ArduPilot 的架構不同但面對的約束一樣。

---

## 1. 第一個決定:為什麼需要 RTOS

假設你照直覺寫一個 `while(1)` 主迴圈:讀感測器、算控制、輸出、寫 log、處理 MAVLink。這個設計在第一次寫 SD 卡時就會壞掉——SD 卡的一次寫入可能耗掉幾十毫秒,而角速率迴路的預算是 1 毫秒。

問題的本質是:**這些工作的即時性要求差了四個數量級,不能放在同一個執行順序裡。**

| 工作 | 週期 | 遲到的後果 |
|---|---|---|
| 角速率控制 | 1 ms | 姿態發散,可能墜機 |
| 姿態控制 | 4 ms | 追蹤變差 |
| 位置控制 | 20 ms | 飄移 |
| MAVLink 收發 | 20~100 ms | 遙測卡頓 |
| 寫 log | 不定 | 少一段記錄 |
| 讀參數 | 不定 | 使用者要多等一下 |

解法是搶佔式即時作業系統:高優先權的任務隨時可以打斷低優先權的。PX4 在真實硬體上跑 NuttX(POSIX 相容的 RTOS),在 SITL 模式下直接跑在 Linux 上。ArduPilot 用自己的 HAL 抽象層,底下可以是 ChibiOS 或 Linux。

**這裡有個對後端工程師的重要提醒**:即時系統的「即時」不是「快」,是「可預測」。一個平均 0.1 ms、偶爾 50 ms 的實作,比穩定 1 ms 的實作糟糕得多。所有會造成不確定延遲的東西——動態記憶體配置、無界的迴圈、可能阻塞的鎖——在即時路徑上都是禁忌。PX4 的規則是啟動後不再做動態配置。

## 2. 第二個決定:work queue,不是一個模組一條執行緒

有了 RTOS,直覺的下一步是每個模組開一條執行緒。問題是**每條執行緒都要自己的堆疊**,幾 KB 起跳,而 PX4 有幾十個模組。RAM 會先爆掉。

PX4 的解法是 work queue:**若干條共用執行緒,依優先權分組,模組把自己註冊成上面的 work item。** 實際的分組(取自 `WorkQueueManager.hpp`):

| Work queue | 放什麼 | 優先權 |
|---|---|---|
| `wq:rate_ctrl` | 角速率控制 | 最高 |
| `wq:SPI0`~`SPI6`、`wq:I2C0`~`I2C4` | 感測器驅動,依匯流排分開 | 高 |
| `wq:INS0`~`INS3` | 慣性導航與估測器,一組 IMU 一個 | 高 |
| `wq:nav_and_controllers` | 姿態、位置控制器與導航 | 次高 |
| `wq:uavcan` | CAN 匯流排 | 中 |
| `wq:ttyS0`~`ttyS9` | 序列埠 | 中 |
| `wq:hp_default` | 其他高優先權工作 | 中 |
| `wq:lp_default` | 低優先權雜項 | 最低 |

這張表本身就是一份架構文件:**它把「什麼東西不能被什麼東西擋住」寫死了。** 角速率控制獨佔最高優先權的佇列,連感測器驅動都不能擋它;log 與參數這類工作被丟到 `lp_default`,愛跑多久跑多久。

按匯流排分佇列(SPI0、SPI1 各一條)也是有意的:同一條 SPI 上的裝置本來就要排隊,分成不同佇列反而增加切換成本;不同匯流排則可以真的並行。

少數模組仍然是獨立任務而非 work item(例如 `commander`、`mavlink`、`logger`),因為它們的工作模式不是「被事件觸發後跑一小段」,而是持續運作或需要自己的執行節奏。

---

## 3. 第三個決定:uORB,模組之間不直接呼叫

模組之間要交換資料。三個選項:

| 做法 | 問題 |
|---|---|
| 直接函式呼叫 | 模組互相知道對方存在,無法單獨替換、單獨測試;呼叫方會被被呼叫方的執行時間綁架 |
| 共享全域變數 + 鎖 | 高優先權任務可能被低優先權任務持有的鎖擋住(優先權反轉),即時性直接破功 |
| 訊息佇列 | 有界佇列會滿,滿了要嘛阻塞(不可接受)要嘛丟棄(誰決定丟哪個) |

PX4 的答案是 uORB:一個**單寫多讀、發佈者永不阻塞**的發佈訂閱匯流排。每個 topic 在記憶體裡是一小塊環形緩衝,發佈者寫入最新值並遞增序號,訂閱者比對自己上次看到的序號來判斷有沒有新資料。

程式碼長這樣(取自 `MulticopterRateControl.hpp`):

```cpp
class MulticopterRateControl : public ModuleBase, public ModuleParams, public px4::WorkItem
{
    // 一般訂閱:自己決定何時去看
    uORB::Subscription _vehicle_control_mode_sub{ORB_ID(vehicle_control_mode)};
    uORB::Subscription _vehicle_rates_setpoint_sub{ORB_ID(vehicle_rates_setpoint)};

    // 回呼訂閱:資料一到就觸發這個 work item 執行
    uORB::SubscriptionCallbackWorkItem _vehicle_angular_velocity_sub{this, ORB_ID(vehicle_angular_velocity)};
};
```

三個基底類別各自負責一件事:`ModuleBase` 提供 `start` / `stop` / `status` 這類命令列介面,`ModuleParams` 讓參數變更能自動通知到模組,`px4::WorkItem` 讓它可以被掛到 work queue 上。這是很乾淨的關注點分離,跟你在後端看到的 mixin 是同一個想法。

### uORB 帶來的三個副作用,其實比主功能還重要

**可完整記錄。** 因為所有跨模組的資料都經過 uORB,`logger` 模組只要訂閱就能記下來。ULog 檔案裡不是「某人印的 log 字串」,而是**系統所有內部狀態的時間序列**。飛行出問題時,你拿到的是完整的狀態演變,不是零散的印出訊息。

**可外部觀察。** `mavlink`、`uxrce_dds_client`、`zenoh` 這幾個模組做的事情本質上一樣:訂閱 uORB 主題,轉成外部協定送出去;反向把外部訊息轉成 uORB 發佈。所以「ROS 2 能看到飛控狀態」不是另外做了介面,是 uORB 被橋接出去而已。

**可離線重播。** PX4 有 `replay` 模組,能把記錄下來的感測器資料重新餵進系統,讓估測器與控制器再跑一次。這等於一個確定性的重現機制:懷疑 EKF 在某次飛行中判斷錯誤,可以改完程式碼用同一份資料再跑,直接比對差異。

後端工程師應該覺得眼熟:**這就是事件溯源。** 把系統狀態變化寫成不可變的事件流,於是得到了稽核、重播、除錯與外部整合能力。差別只在於這裡的事件是每秒幾千則的感測器資料,而且要在 1 MB RAM 裡完成。

## 4. 第四個決定:資料驅動排程,不是定時器

直覺的做法是讓角速率控制器每 1 ms 被定時器叫醒一次。PX4 沒有這樣做,而是讓它被 `vehicle_angular_velocity` 這個主題的**發佈事件**觸發(上面那個 `SubscriptionCallbackWorkItem`)。

理由是延遲。如果用固定週期的定時器,IMU 資料抵達的時間點與控制器醒來的時間點沒有對齊,平均會多等半個週期。改成資料驅動之後,感測器資料一寫進 uORB,控制器立刻被排進最高優先權佇列。省下的那半個週期,在 [00 章算過的預算表](../00-system-overview/01-the-control-loop.md)裡是實打實的相位裕度。

這也帶來一個副作用:**控制器的執行頻率由感測器決定。** 換一顆取樣率不同的 IMU,整條控制鏈的節奏就變了。所以 PX4 有一層 `vehicle_angular_velocity` 的產生機制負責把不同 IMU 統一成一致的輸出頻率,而不是讓每個下游自己處理。

## 5. 參數系統:為什麼不用設定檔

飛控有上千個可調整的量(控制增益、感測器旋轉、failsafe 門檻、機型幾何)。用設定檔的話,每次調參要重開機,而調 PID 需要在飛行中即時改。

所以參數是一套**執行期的鍵值儲存**,具備幾個設定檔給不了的性質:飛行中可寫入、寫入後模組收到通知(這就是 `ModuleParams` 的用途)、有型別與範圍中繼資料所以地面站能自動產生 UI、變更會存進非揮發記憶體、而且每個參數的名稱是全域唯一的短字串(`MC_ROLLRATE_P` 這種)。

對軟體工程師來說,關鍵認知是:**參數是飛控最重要的對外介面之一。** 地面站的校正流程、調參精靈、機型設定,全部建立在參數的中繼資料上。你加一個新模組時如果沒有正確宣告參數的中繼資料,它在地面站上就會是一個沒有說明、沒有範圍限制的裸數字。

## 6. 啟動流程:為什麼是 shell 腳本

PX4 開機時跑的是 ROMFS 裡的一組 shell 腳本(`rcS` 與 `init.d` 底下的機型設定)。在一個處處講究即時性的系統裡放 shell 腳本,看起來很奇怪。

理由是**組態的組合爆炸**。同一份韌體要能跑四旋翼、六旋翼、固定翼、VTOL、無人船,每種機型要啟動的模組不同、參數預設值不同、輸出對應不同。如果這些都在編譯期決定,就得為每種機型出一版韌體。用啟動腳本的話,一份韌體加上一個機型編號就能決定要啟動哪些模組。

要決定「這塊板子的韌體裡包含哪些模組」則是編譯期的事(板子的 `.px4board` 設定檔),因為 flash 空間有限,不可能什麼都塞。所以是兩層:**編譯期決定有哪些能用,啟動期決定實際跑哪些。**

## 7. 模組地圖

PX4 main 分支的 `src/modules/` 底下大約有六十個模組。按角色分:

| 角色 | 模組 | 做什麼 |
|---|---|---|
| 感測 | `sensors`、`rc_update`、`airspeed_selector`、`temperature_compensation` | 把原始感測器資料整理成統一、校正過的形式 |
| 估測 | `ekf2`、`attitude_estimator_q`、`local_position_estimator`、`mag_bias_estimator` | 融合感測器成為狀態估計 |
| 控制 | `mc_rate_control`、`mc_att_control`、`mc_pos_control`、`fw_*`、`rover_*`、`vtol_att_control` | 各種載具型態的控制律 |
| 分配 | `control_allocator` | 把力與力矩需求轉成各致動器輸出 |
| 決策 | `commander`、`flight_mode_manager`、`navigator`、`land_detector` | 模式管理、failsafe、任務執行、著陸判定 |
| 通訊 | `mavlink`、`uxrce_dds_client`、`zenoh` | 對外協定 |
| 系統 | `logger`、`dataman`、`load_mon`、`events`、`task_watchdog` | 記錄、持久化、資源監控 |
| 酬載 | `gimbal`、`camera_feedback`、`payload_deliverer` | 任務裝備 |
| 測試 | `failure_injection_manager`、`replay`、`simulation` | 故障注入與重播 |

值得注意的是這幾年新增的方向:`mc_nn_control`(類神經網路控制)、`spacecraft`、`rover_ackermann` / `rover_differential` / `rover_mecanum`。飛控韌體正在變成「各種載具的即時控制平台」,不只是飛機。

## 8. 可觀測性

在一台看不到、摸不到、正在天上飛的電腦上除錯,可觀測性是生死問題。飛控提供的手段:

| 手段 | 給你什麼 |
|---|---|
| ULog | 所有 uORB 主題的時間序列,事後完整重建 |
| `perf` 計數器 | 每個 work item 的執行次數、平均耗時、最大耗時、超時次數 |
| `top` / `work_queue status` | 各執行緒與佇列的 CPU 佔用與堆疊使用 |
| `listener <topic>` | 在系統主控台上即時印出某個 uORB 主題 |
| `events` 子系統 | 結構化的事件與警告,會轉成地面站的訊息 |
| `dmesg` | 開機與驅動層的訊息 |

`perf` 特別值得強調。模組裡那行 `perf_counter_t _loop_perf` 不是裝飾:它記錄這個控制迴圈實際跑了多久、最壞情況多久、有沒有超過預算。**即時系統的效能問題看的是最大值不是平均值**,這個計數器就是為此而存在。

排查「飛機抖動」這類問題時,先看 `perf` 的最大耗時與超時次數,往往比一頭鑽進控制參數有效得多。

---

## 9. 這一章的結論

1. 即時性要求差四個數量級的工作不能混在一起跑,所以需要 RTOS 的搶佔式排程。
2. 每模組一執行緒會耗盡 RAM,所以改用依優先權分組的 work queue;那張分組表就是「誰不能擋誰」的規格。
3. 模組間用 uORB 這個單寫多讀、不阻塞的發佈訂閱匯流排,順帶得到完整記錄、外部橋接與離線重播——本質上是事件溯源。
4. 控制器由感測器資料觸發而非定時器,為的是省下半個週期的相位裕度。
5. 參數是執行期的鍵值儲存,也是地面站賴以生成 UI 的介面契約。
6. 編譯期決定韌體含哪些模組,啟動腳本決定實際跑哪些,兩層分工解決機型組合爆炸。
