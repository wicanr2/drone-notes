# 影像管線與感知迴路:延遲決定一切

影像這一塊最常見的錯誤認知是「畫質優先」。實際上在無人機系統裡,**延遲幾乎永遠比畫質重要**——操作者靠畫面判斷要不要閃避,追蹤演算法靠畫面算誤差,兩者都是控制迴路,而控制迴路對延遲的容忍度是有硬上限的。

這一章把影像從感光到顯示的每一段延遲攤開,然後說明為什麼一個 200 毫秒延遲的影像流,會讓視覺追蹤的反應速度被鎖死在 0.4 Hz。

---

## 1. 延遲從哪裡來

從光子打到感測器到畫面出現在螢幕上,中間有七段。以 30 fps、1080p、硬體編碼的典型配置估:

| 階段 | 典型延遲 | 可壓縮性 |
|---|---|---|
| 曝光與讀出 | 一個影格時間(30 fps → 33 ms) | 提高幀率可減少 |
| ISP 處理(去馬賽克、白平衡、降噪) | 5~15 ms | 關掉重度降噪可減少 |
| 編碼 | 10~30 ms | **B 影格與 look-ahead 是主因** |
| 封包化與傳送 | 1~5 ms | 幾乎不可壓 |
| 網路傳輸 | 5~50 ms | 看鏈路 |
| 接收端抖動緩衝 | **30~200 ms** | **最大且最常被忽略的一段** |
| 解碼與顯示合成 | 20~50 ms | 顯示器的更新率是下限 |
| **合計** | **約 100~380 ms** | |

兩個可壓縮空間最大的地方值得單獨說:

**B 影格。** 它靠前後兩個方向的影格做預測,壓縮率好,但編碼器必須先拿到後面的影格才能編當前這張,直接製造一個影格以上的延遲。**即時應用一律關掉 B 影格。** 同理,look-ahead 與多遍編碼也要關。

**抖動緩衝。** 播放端為了讓畫面順暢,會先囤積一段資料再開始播。預設值常常是幾百毫秒——這一項往往比整條網路鏈路的延遲還大。做即時監控時要把它調到最小,代價是網路抖動時畫面會頓,那是正確的取捨。

判斷自己的管線有多慢有個土法很好用:**拿手機碼表對著鏡頭拍,再把螢幕上的畫面跟真實碼表一起入鏡拍照**,兩個讀數的差就是端到端延遲。比看規格書可靠。

## 2. 傳輸協定怎麼選

| 協定 | 延遲 | 穿 NAT | 瀏覽器可看 | 適合 |
|---|---|---|---|---|
| 裸 RTP / UDP | 最低 | 不行 | 不行 | 同一區網,機上到地面站 |
| RTSP | 低 | 不行(需埠對應) | 不行(需外掛) | 傳統監控整合、地面站顯示 |
| WebRTC | 低 | **可以** | **可以** | 給雲端與瀏覽器看 |
| SRT | 低到中 | 可(需設定) | 不行 | 不穩定的長途鏈路,有重傳與加密 |
| HLS / DASH | 高(秒級) | 可以 | 可以 | 錄影回放,**不適合即時操作** |

選擇邏輯很直接:**機上到地面站用 RTP 或 RTSP;要進瀏覽器或跨網際網路用 WebRTC;鏈路品質差又需要重傳用 SRT;HLS 只用於事後回放。**

把 HLS 拿來做即時監控是常見的誤用。它的分段機制天生就有數秒延遲,對錄影回放很好,對「操作者要即時判斷」完全不能用。

### MAVLink 在這裡的角色

影像不走 MAVLink,但 MAVLink 負責**告訴地面站影像在哪裡**:相機資訊與影像串流資訊這類訊息帶著串流的 URL、解析度、幀率、編碼格式。地面站據此自己去連。

所以「QGC 看不到影像」要分兩段查:是沒收到串流資訊訊息(MAVLink 這一段的問題),還是收到了但連不上那個 URL(網路或編碼的問題)。分不清楚這兩段,會在錯的地方查很久。

## 3. 機上感知:幀率與延遲的取捨

在機上跑物件偵測時,會遇到一個看似矛盾的選擇:模型跑 10 fps 但延遲 100 ms,還是跑 30 fps 但延遲 200 ms?

答案幾乎永遠是**選延遲低的**。原因在下一節會算給你看:延遲直接限制控制迴路的頻寬,而幀率只影響取樣密度。在同樣的計算預算下,寧可用小一點的模型換低延遲。

其他幾個實務要點:

**丟幀比排隊好。** 如果推論跟不上輸入,要丟掉舊影格處理最新的,不要讓佇列累積。佇列累積的結果是延遲越來越大,而且畫面看起來還很順——這是最難察覺的失效模式。

**每一幀都要帶擷取時刻的時間戳。** 不是處理完的時刻,是**曝光的時刻**。後面所有的座標換算與融合都依賴這個。

**輸出要帶它所依據的姿態。** 一個框的像素座標要換成地面位置,需要當時的姿態與位置。正確的做法是在擷取時刻就把姿態一起記下來,而不是在偵測完成後才去問「現在的姿態是什麼」——那時候飛機已經轉過去了。

## 4. 視覺伺服:為什麼追蹤會震盪或跟不上

目標追蹤的典型迴路:偵測出目標框 → 算出框中心與畫面中心的偏差 → 換成雲台的角速率指令 → 雲台轉動 → 目標回到畫面中心。

這是一個標準的負回授控制迴路,所以[第一章那條公式](../00-system-overview/01-the-control-loop.md)直接適用:

```
φ = ω · τ
```

假設整條影像管線加上推論的延遲是 200 毫秒,而我們願意付出 30° 的相位落後:

```
ω_max = (30° = 0.524 rad) / 0.2 s = 2.6 rad/s ≈ 0.42 Hz
```

**這個迴路的反應速度上限就是 0.4 Hz,大約要 2 秒多才能穩定下來。** 不管你怎麼調增益都不會更快:調高會震盪(相位落後超過裕度),調低會更慢。

這解釋了兩個現場常見的現象:

- **「追蹤一直抖」**:增益調太高,延遲造成的相位落後讓它變成正回授。
- **「目標跑掉就追不回來」**:迴路頻寬只有 0.4 Hz,目標移動快過這個速度就跟不上。

而正確的解法是**降低延遲**,不是調增益。延遲砍半,可用頻寬就加倍。所以在追蹤應用裡,把推論模型換小一號、關掉 B 影格、縮小抖動緩衝,效果遠大於調參數。

### 雲台與機體的分工

三軸雲台可以獨立轉動,反應比整台飛機轉向快得多。合理的分工是:

- **快的部分交給雲台**:小幅度、高頻的追蹤修正。
- **慢的部分交給機體**:雲台的偏航角快用完時,請機體轉過去,把雲台的可動範圍讓出來。

這是兩個時間尺度分開的典型例子,跟[責任邊界那章](../00-system-overview/02-system-boundaries.md)的避障分層是同一個模式。

## 5. 常見問題對照

| 症狀 | 先查 | 常見原因 |
|---|---|---|
| 畫面延遲很大但很順 | 抖動緩衝設定、推論佇列長度 | 緩衝或佇列在累積 |
| 畫面會頓但延遲低 | 網路抖動、丟包率 | 緩衝調太小,或鏈路不穩 |
| 地面站完全沒畫面 | 有沒有收到串流資訊訊息 | MAVLink 那段沒通,或 URL 錯 |
| 有畫面但花屏 | 關鍵影格間隔、丟包 | 丟了關鍵影格要等下一個才能恢復 |
| 追蹤抖動 | 端到端延遲、迴路增益 | 增益超過延遲允許的上限 |
| 框的位置換算到地面差很多 | 時間戳、姿態對齊 | 用了偵測完成時的姿態而非擷取時的 |
| 飛久了畫面延遲越來越大 | 佇列與記憶體 | 沒有丟幀策略 |
| 地面待命時畫面變差 | 溫度與降頻 | 熱節流,編碼器降規格 |

## 6. 這一章的結論

1. 端到端延遲典型在 100~380 毫秒,最大的兩塊是編碼的 B 影格與接收端的抖動緩衝,兩者都可以調。
2. 傳輸協定按「要不要穿 NAT、要不要進瀏覽器」選;HLS 不能用於即時操作。
3. 影像不走 MAVLink,但 MAVLink 負責告知串流位置,查問題要把這兩段分開。
4. 機上推論在同樣預算下優先選低延遲,而且要丟幀不要排隊。
5. 每一幀要帶曝光時刻的時間戳與當時的姿態,否則座標換算會系統性偏差。
6. 視覺追蹤迴路的頻寬被延遲鎖死(200 毫秒延遲 → 約 0.4 Hz),抖動與跟不上都是這個上限的表現,解法是降延遲不是調增益。
