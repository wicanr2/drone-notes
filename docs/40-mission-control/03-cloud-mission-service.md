# 雲端任務服務:跟一般後端差在哪

這一層對後端工程師來說有八成是熟悉的:REST API、資料庫、佇列、權限、稽核。所以這一章不談那八成,只談**不一樣的兩成**——那兩成如果用一般後端的預設假設去做,系統會在現場出事。

四個關鍵差異:

1. **連線不是偶爾斷,是經常斷。** 離線必須是設計內的正常路徑,不是異常處理。
2. **指令有物理後果而且不可回滾。** 「重送一次應該沒關係」在這裡可能等於「飛了兩趟」。
3. **狀態的權威在遠端而且會自己推進。** 你不是唯一的寫入者,機上會在你看不到的時候繼續改變狀態。
4. **有法規層級的稽核需求。** 誰在什麼時候批准了什麼飛行,可能要保存數年並接受查核。

---

## 1. 資料模型:三種東西不要混在一起

最常見的設計錯誤是用一張 `missions` 表把定義、計畫與執行狀態全放進去,然後用 `status` 欄位表示一切。這在第一次「同一條航線飛第二趟」時就會壞掉。

正確的切法:

```
Vehicle              機:序號、型號、能力(續航、酬載)、韌體版本、目前狀態
Operator             操作者:身分、證照、權限

MissionDefinition    任務定義:做什麼(區域、目標、動作序列),不可變、版本化
MissionPlan          執行計畫:哪台機、什麼時窗、什麼參數,綁定一個定義版本
Execution            一次實際執行:狀態、進度序號、起訖時間、結果
ExecutionEvent       事件流:append-only,每筆帶進度序號與發生時刻
Artifact             成果:照片、影片、飛行紀錄的索引與儲存位置
Incident             異常:failsafe 觸發、人工介入、中止,含當時的完整脈絡
```

三層分離的理由:

**定義不可變且版本化**,因為稽核時要能回答「當時執行的到底是哪一版的任務內容」。改了定義而沒有版本,歷史紀錄就失去意義。

**計畫與執行分開**,因為一個計畫可能執行多次(第一次因天候中止、第二次完成),而每次執行的事件流是獨立的。

**事件流是 append-only**,這是[整個三層架構的最終一致性基礎](01-three-layers.md):機上是寫入端,雲端把事件寫進不可變的流,再投影成當前狀態。這正是事件溯源加上 CQRS 的標準形狀,不是為了時髦,是因為斷線重連的語意本來就需要它。

## 2. API:冪等是硬需求

派工的 API 至少要滿足:

**冪等鍵是「計畫 ID + 版本」。** 同一個計畫的同一版重送任意次,機上只會接受一次。網路重試、雲端重啟、操作者連點兩下,都不能造成飛兩趟。

**要改任務就發新版本,不要改舊版本。** 機上以版本號決定要不要套用,而且[在動作邊界才套用](01-three-layers.md)。

**下發是意圖,不是指令。** 送的是「請執行計畫 X 版本 N」,不是「現在起飛」。機上有權拒絕(電量不足、位置不對、正在執行別的任務),而拒絕要帶原因。

**取消要有明確語意。** 「取消」是指停止派發、讓已經在飛的繼續飛完,還是指中止飛行?這兩件事要用不同的操作,不要用同一個 `cancel`。實務上至少要分「撤回未開始的計畫」與「請求中止進行中的執行」。

### 狀態查詢的兩種讀法

| 讀法 | 用途 | 資料來源 |
|---|---|---|
| 最後已知狀態 | 一般清單、儀表板 | 事件流的投影 |
| 即時狀態 | 現場監控 | 直接訂閱遙測串流 |

要在 API 上把兩者區分清楚,並且**永遠附上「這份資料是什麼時候的」**。無人機系統裡「五分鐘前的位置」跟「現在的位置」差別可能是好幾公里,一個沒有時間戳的位置欄位會誤導操作者。

## 3. 事件:亂序、重複、遲到都是常態

機上緩衝的事件在重連後補送,所以雲端會遇到:

- **重複**:同一筆事件送了兩次 → 用「執行 ID + 進度序號」去重
- **亂序**:序號 7 比序號 5 先到 → 依序號排序,不要以到達順序為準
- **遲到**:任務結束半小時後才收到中間的事件 → 事件流照樣接受,投影重算
- **永遠不到**:機器摔了、儲存壞了 → 投影要能處理缺口,標記為未知而不是假設

實作上的建議:

**投影要能重放。** 事件流是真相,當前狀態是投影。改了業務規則就重放事件重新投影,不要去改歷史狀態。

**永遠不回頭。** 收到序號比當前小的事件,只寫進事件流,不改當前狀態。

**缺口要顯示出來。** 收到序號 3、4、7,就知道缺了 5 和 6。介面上要能看出這件事,而不是安靜地跳過——那個缺口可能正是出事的地方。

## 4. 派工:選機比想像中複雜

「把任務派給空的那台」在示範時很好用,在營運環境會出問題。實際要考慮的:

| 條件 | 為什麼 |
|---|---|
| 電量與電池健康度 | 不只看當前電量,還要看這顆電池衰退到什麼程度 |
| 位置與轉場時間 | 最近的不一定最快,要看轉場路線 |
| 酬載匹配 | 有沒有裝任務需要的相機或感測器 |
| 韌體與軟體版本 | 舊版本可能不支援任務裡的某個動作 |
| 維護狀態 | 累積飛行時數、待檢項目 |
| 法規限制 | 這台機在這個空域是否被允許、操作者證照是否涵蓋 |
| 時窗與天候 | 風速、降雨、日落時間 |
| 空域申請狀態 | 有沒有取得許可,見下一節 |

比較務實的做法是**兩階段**:先用硬條件過濾出可行集合(酬載、版本、法規),再用成本函數排序(電量、距離、維護)。硬條件不過的機器要能說出原因,因為「為什麼這台沒被派到」是營運端最常問的問題。

## 5. 離線:設計成正常路徑

具體要做到:

**機上有完整的離線能力。** 任務內容、地圖資料、地形高程都要能預先下載。飛到收訊死角不能導致任務失敗。

**事件緩衝要有上限與淘汰策略。** 儲存空間會滿,要決定滿了之後丟哪些(通常保留關鍵事件與異常,丟掉高頻的位置更新)。

**補送要限速。** 十台機同時恢復連線並補送半天的事件,會把服務打爆。補送要排隊並限流。

**重連後先對齊再互動。** 機上回報「我在執行 X,版本 N,進度序號 M」,雲端據此決定要不要下發新版本,而不是直接開始下命令。

**時鐘不可信。** 機上的時間戳可能因為沒有 GNSS 授時而偏移。事件要同時帶機上時間與雲端接收時間,分析時才分得清楚。

## 6. 多機協調:能做什麼、不能做什麼

| 在雲端做 | 不在雲端做 |
|---|---|
| 空域分配、時窗排程 | 即時避讓 |
| 航線衝突的事前檢查 | 飛行中的距離保持 |
| 任務分配與負載平衡 | 編隊控制 |
| 充電站與起降場的排隊 | 起降時的最後間隔 |

判準還是[延遲預算](../00-system-overview/01-the-control-loop.md):雲端能處理的是分鐘尺度的戰略決策,秒尺度的戰術動作必須在機上或機間直連完成。

實務上這條線常被越過,因為在示範環境裡雲端做即時協調看起來可行——區網延遲低、機少、沒有干擾。到了現場,鏈路一抖就出事。

## 7. 合規與稽核

這一層有兩件事是一般後端不會遇到的:

**Remote ID。** 法規要求無人機對外廣播身分與位置。廣播式(藍牙 / Wi-Fi)由機上硬體或韌體處理,雲端不參與;網路式則需要把資料送到指定的服務。開源的實作有 [opendroneid-core-c](https://github.com/opendroneid/opendroneid-core-c)(廣播式編碼)與 [InterUSS](https://github.com/interuss/dss)(網路式與空域協調)。

注意 Remote ID 的目的跟資安相反:**它是刻意要讓別人知道你是誰、你在哪。** 設計時不要把它跟營運資料的保密需求混在一起。

**稽核紀錄。** 誰批准了這次飛行、當時的任務內容是哪一版、飛行過程發生了什麼、誰在什麼時候介入。這些要能在事後查證,而且要防止事後竄改。做法不必複雜:append-only 的事件流、關鍵決策留下操作者身分與時間、重要紀錄做雜湊鏈或寫進 WORM 儲存。

實際的法規要求依國別差異很大且更新頻繁,**要以主管機關的現行條文為準**。本文只講制度設計對系統架構的影響。

## 8. 通訊通道怎麼選

雲端與機上之間的長連線通道:

| 方案 | 優點 | 要注意 |
|---|---|---|
| MQTT | 為不穩定網路設計,有 QoS 與遺囑訊息,生態成熟 | 訊息大小與主題設計要規劃,否則難以演進 |
| WebSocket | 實作簡單,穿防火牆容易 | 重連、心跳、背壓要自己做 |
| gRPC streaming | 型別安全、雙向串流 | 對行動網路的斷線恢復要額外處理 |
| Zenoh | 為高延遲與跨網段設計,可跟 ROS 2 生態接上 | 較新,團隊要投入學習 |

MQTT 的**遺囑訊息**在這個場景特別好用:機器斷線時,伺服器會自動代它發出一則預先登記的訊息,讓系統知道它掉了,而不是等逾時。

不論選哪個,原則一樣:**通道只負責搬東西,語意放在應用層。** 不要依賴通道的送達保證來當作業務的可靠性保證——因為機器可能在收到之後、執行之前就重開了。

## 9. 常見錯誤

| 錯誤 | 後果 |
|---|---|
| 用單一 `missions` 表混合定義、計畫與執行 | 同一任務飛第二趟時資料模型就不夠用 |
| 派工沒有冪等鍵 | 網路重試造成飛兩趟 |
| 用可變狀態當真相,事件只當日誌 | 斷線重連時衝突無解 |
| 位置欄位沒有時間戳 | 操作者看著五分鐘前的位置做決策 |
| 雲端做即時協調 | 示範可行,現場鏈路一抖就出事 |
| 「取消」語意不清 | 操作者以為只是不派了,實際上飛機被中止在半空 |
| 補送不限流 | 多機同時恢復連線把服務打爆 |
| 稽核紀錄可被後台修改 | 出事時無法自證 |

---

## 10. 這一章的結論

1. 跟一般後端的差異在四點:經常斷線、指令不可回滾、狀態權威在遠端、有法規稽核。
2. 定義、計畫、執行要分成三種實體;定義不可變且版本化,事件流 append-only。
3. 冪等鍵是「計畫 ID + 版本」;要改任務就發新版本;下發的是意圖不是指令,機上有權拒絕。
4. 事件的重複、亂序、遲到、遺失都是常態;投影要能重放,缺口要顯示出來。
5. 選機要先用硬條件過濾再用成本函數排序,而且要能說明為什麼某台沒被選上。
6. 雲端做分鐘尺度的戰略協調,秒尺度的戰術動作留給機上。
7. Remote ID 的目的是公開身分,跟營運資料保密是兩件事,不要混在一起設計。
