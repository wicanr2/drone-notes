# MAVLink 為什麼長這樣

第一次看 MAVLink 的人常有幾個困惑:為什麼欄位這麼省?為什麼沒有連線的概念?為什麼有些命令要等確認、有些直接送出去就算?為什麼同一件事有 `COMMAND_LONG` 和 `COMMAND_INT` 兩個版本?

這些設計不是隨意的。把它放回原本的約束——**一條 57600 bps、會掉包、沒有重傳、單向可能斷掉的無線電鏈路**——每一個選擇都會變得理所當然。這一章就是做這件事。

---

## 1. 約束是什麼

先把環境條件講清楚,後面所有推導都從這裡出發:

| 條件 | 數字 |
|---|---|
| 典型遙測鏈路速率 | 57600 bps(SiK 無線電),實際可用約六成 |
| 封包遺失率 | 空曠好天氣幾個百分比,邊界距離可到雙位數 |
| 往返延遲 | 數十到數百毫秒,抖動大 |
| 鏈路對稱性 | 常是半雙工,上下行搶同一段時間 |
| 節點數量 | 一台機上可能有飛控、雲台、相機、伴隨電腦數個元件 |
| 執行環境 | 一端是幾百 KB RAM 的 MCU |

再加一個常被忽略的:**這條鏈路上跑的是安全關鍵的資料**。姿態顯示晚一秒不會摔機,但一則錯誤解析的命令會。

---

## 2. 從約束推封包格式

### 為什麼是二進位而不是 JSON

算一下就知道。一則姿態訊息要傳時間戳與六個浮點數。二進位是 28 位元組;等價的 JSON 大約 150 位元組,超過五倍。在 5760 位元組/秒的鏈路上,這個差距直接決定了姿態能不能用 50 Hz 更新。

代價是不可讀、必須有共用的訊息定義。這個交換在頻寬便宜的環境不划算,在這裡划算。

### 封包長什麼樣

MAVLink v2 的一則封包:

```
+------+------+----------+----------+------+-------+--------+---------+---------+----------+-----------+
| STX  | LEN  | INCOMPAT | COMPAT   | SEQ  | SYSID | COMPID | MSGID   | PAYLOAD | CHECKSUM | SIGNATURE |
| 1 B  | 1 B  |   1 B    |   1 B    | 1 B  |  1 B  |  1 B   |  3 B    | 0~255 B |   2 B    |  13 B(選) |
+------+------+----------+----------+------+-------+--------+---------+---------+----------+-----------+
        \___________________________ 固定開銷 12 位元組 ___________________________/
```

每個欄位都在解決一個具體問題:

| 欄位 | 解決什麼 |
|---|---|
| `STX` 起始位元組 | 在位元組流裡找到封包邊界。序列埠沒有封包概念,收到的是連續位元組,必須自己同步 |
| `LEN` | 知道要讀多少;搭配 v2 的尾端零位元組截斷,短資料可以更短 |
| `INCOMPAT` / `COMPAT` 旗標 | 協定演進用。不認得 incompat 旗標就必須丟棄該封包,認不得 compat 旗標可以照常處理 |
| `SEQ` 序號 | 偵測掉包。注意它只用來算掉包率,**不做重送** |
| `SYSID` / `COMPID` | 定址。誰發的、發給誰的判斷都靠這兩個位元組 |
| `MSGID` 3 位元組 | v1 只有 1 位元組,255 種訊息很快用完,v2 擴到 1600 萬種以容納廠商自訂 |
| `CHECKSUM` | 偵錯,而且不只偵錯——見下面 |

### CRC 裡藏了訊息定義的指紋

MAVLink 的校驗和不只算封包內容,還會把一個從**訊息定義本身算出來的種子**(`crc_extra`)混進去。這個種子由訊息名稱與所有欄位的型別、名稱決定。

它擋住的問題是:兩端用了不同版本的訊息定義,某個欄位從 `uint16` 變成 `uint32`。如果只算內容的 CRC,封包會通過校驗,然後被錯誤解析——你會得到一個看起來合理但完全錯誤的數值。加了定義指紋之後,定義不一致的封包會**校驗失敗而被丟棄**,問題在傳輸層就暴露,而不是變成一個詭異的飛行行為。

這是很值得學的設計:**在安全關鍵的系統裡,寧可明顯地失敗,也不要安靜地誤解。**

### 為什麼沒有連線

MAVLink 沒有握手、沒有 session、沒有連線狀態。任何節點隨時可以開始送,收到的節點自己判斷要不要處理。

理由是廣播式的鏈路本來就沒有連線可言:一台地面站、一台記錄器、一台中繼可能同時聽同一段無線電。加上連線狀態只會製造一個新的失效模式——連線斷了要重連,重連期間資料就沒了。

取而代之的是 `HEARTBEAT`:每個元件每秒廣播一次「我還在,我是什麼型別,我現在什麼狀態」。**存活判定由接收端自己做**(通常是連續幾次沒收到就標記失聯)。這是最終一致性的思路,不是連線導向的思路。

## 3. 定址:sysid 與 compid

MAVLink 用兩個位元組定址:

- **System ID**:一台載具一個,同一個網路裡要唯一。地面站通常也佔一個。
- **Component ID**:一台載具上的各個元件。飛控慣例是 1,雲台、相機、伴隨電腦各有慣例區段。

這代表兩件事對開發很重要:

**一台機不是一個節點,是一組節點。** 你的雲台控制指令要送給雲台的 compid,不是飛控的。很多「雲台不動」的問題就是指令送錯元件。

**sysid 只有 8 位元。** 同一個 MAVLink 網路裡最多 255 台。要管上千台機的機隊,不能靠單一 MAVLink 網路把它們串起來——這是[雲端架構](../50-gcs-and-cloud/)必須處理的問題,而不是協定層能解的。

## 4. 三類互動,三種可靠性策略

MAVLink 的訊息不是同一種東西,它們有三種截然不同的可靠性需求,協定也用了三種不同的處理:

### 串流:掉了就算了

姿態、位置、電池這類狀態,以固定頻率不斷發送。**不重送、不確認。** 因為下一筆很快就到了,重送一筆過期的姿態沒有意義,只是浪費頻寬。

接收端要照這個假設寫:掉包是正常的,不要把「這一筆沒收到」當成異常。用最新值,不要試圖補齊。

### 命令:要確認

`COMMAND_LONG` / `COMMAND_INT` 送出去之後,對方要回 `COMMAND_ACK`,裡面帶結果碼(接受、拒絕、暫時拒絕、不支援、失敗)。

發送端要做的是**逾時重送 + 冪等假設**:沒收到 ACK 就重送,而接收端要能容忍重複收到同一個命令。這是應用層自己實作的 stop-and-wait,因為傳輸層不提供。

寫程式時最常見的錯誤是**送出去就當成功**。命令被拒絕是常態(pre-arm 沒過、模式條件不滿足、參數超範圍),不看 ACK 的程式會在拒絕時完全沒有反應,操作者只看到「按了沒事發生」。

### 批次資料:要交握

任務航點、參數、日誌檔這類資料是**一整批而且不能少**。MAVLink 為它們定義了交握流程,例如上傳任務是:送出項目數 → 對方逐項索取 → 一項一項回應 → 對方回覆確認。

看起來很囉嗦,但它在丟包鏈路上是對的:接收端主導索取,所以它知道自己缺哪一項;每一項都有明確的請求與回應,掉了就重問那一項,不必重傳整批。

**這其實是在不可靠鏈路上手工做了一層可靠傳輸。** 理解這一點之後,就不會想繞過交握直接送——那條路在實驗室的乾淨鏈路上會通,在現場會壞。

## 5. `COMMAND_LONG` 與 `COMMAND_INT` 的差別

同一個命令為什麼有兩個版本?答案是浮點數精度。

`COMMAND_LONG` 的七個參數都是 32 位元浮點數。32 位元浮點數的有效位數約七位十進位數字。經度 121.5678901 度需要十位有效數字才能表示到公分等級——放進 float32 會被截掉,誤差可以到公尺級。

`COMMAND_INT` 把座標欄位改成 32 位元整數,單位是 1e-7 度。這樣經緯度可以精確表示到約 1 公分,而且沒有浮點數的表示誤差。

實務規則:**牽涉座標的命令一律用 `COMMAND_INT`。** 這也是為什麼任務項目用的是 `MISSION_ITEM_INT` 而不是舊的 `MISSION_ITEM`。

這個坑值得記住,因為它的症狀很陰險:功能看起來正常運作,只是位置有幾公尺偏差,而幾公尺在測繪或精準降落的應用裡就是失敗。

## 6. MAVLink 2 的兩個增量

### 訊息簽章

MAVLink 預設不加密也不驗證。任何人只要能發射同頻段的訊號,就可以送一則 `MAV_CMD_NAV_LAND` 給你的飛機。

v2 提供**簽章**:封包尾端多 13 位元組,內容是用共享金鑰算出的截斷雜湊加上時間戳。它提供的是**來源驗證與重放保護**,不是保密——內容仍然是明文,只是別人偽造不了。

要保密就得靠上層:VPN、加密的鏈路層,或在應用層加密酬載。實務上多數團隊的做法是把 MAVLink 跑在一條加密隧道裡,而不是依賴協定本身。

### 欄位擴充

v2 允許在訊息定義的尾端加欄位,舊版接收端會忽略多出來的部分。這讓協定可以演進而不破壞相容性——標準的向後相容設計,但在嵌入式協定裡不是必然,值得肯定。

## 7. 常見誤解

**「MAVLink 很慢」。** 協定本身開銷只有 12 位元組。慢的是鏈路。看到延遲問題要先量鏈路,不要怪協定。

**「用 MAVLink 傳影像」。** 見[責任邊界那一章](../00-system-overview/02-system-boundaries.md)。控制平面與資料平面要分開。

**「掉包代表鏈路壞了」。** 掉包是設計前提。要看的是掉包率的趨勢與 `SEQ` 的統計,不是「有沒有掉」。

**「送出命令等於執行」。** 沒看 `COMMAND_ACK` 就不知道發生了什麼。

**「sysid 隨便設」。** 同一網路裡重複的 sysid 會造成非常難查的錯亂,因為兩台機的訊息會被當成同一台。

---

## 8. 這一章的結論

1. 二進位、緊湊格式、無連線,都是窄頻寬與丟包鏈路逼出來的選擇。
2. CRC 裡混入訊息定義的指紋,讓版本不一致變成明顯的校驗失敗,而不是安靜的誤解。
3. 定址是 sysid + compid 兩層,一台機是一組元件而不是一個節點。
4. 三類互動配三種可靠性策略:串流不重送、命令要 ACK、批次資料要交握。
5. 座標一律用整數版本的命令與任務項目,避免 float32 的精度損失。
6. v2 的簽章提供來源驗證與重放保護,不提供保密。
