# 機隊營運與資料治理:先算資料量再談架構

從一台機變成一支機隊,技術上最大的變化不是「多幾個連線」,而是**資料量突然變成主要成本**。多數團隊在示範階段沒感覺,上線半年後才發現雲端帳單的組成裡儲存與流量佔了七成。

這一章先把數字算出來,再談架構怎麼配合。

---

## 1. 先算一趟任務產生多少資料

以一趟 30 分鐘的巡檢任務估:

| 資料 | 規格 | 大小 |
|---|---|---|
| 4K 影片 | 25 Mbps × 1800 秒 | **5.6 GB** |
| 高解析照片 | 500 張 × 20 MB | **10 GB** |
| 飛行紀錄(ULog) | — | 約 50 MB |
| 遙測事件 | — | 數 MB |
| **單趟合計** | | **約 15.7 GB** |

放大到營運規模:

```
10 台機 × 每天 5 趟 = 50 趟/天
50 × 15.7 GB ≈ 785 GB/天
785 GB × 365 ≈ 287 TB/年
```

**這個數字會決定你的架構,而不是反過來。** 三個立刻浮現的結論:

1. **原始影像不可能無限期存在熱儲存。** 要有分層與淘汰政策。
2. **上傳頻寬是瓶頸。** 785 GB/天平均是 73 Mbps 持續上傳,而且不會平均——大家傍晚一起回來。
3. **值錢的不是原始資料,是萃取結果。** 十萬張照片裡真正被人看過的可能不到千分之一。

---

## 2. 資料分層與生命週期

| 層 | 內容 | 保留 | 儲存 |
|---|---|---|---|
| 熱 | 最近的任務、待審的成果、告警相關資料 | 7~30 天 | 一般物件儲存 |
| 溫 | 已完成任務的原始影像 | 3~12 個月 | 低頻存取層 |
| 冷 | 法規要求保存的飛行紀錄與稽核事件 | 依法規,可能數年 | 歸檔儲存 |
| 永久 | 萃取結果、報告、缺陷紀錄、統計 | 永久 | 資料庫 |

幾條實務規則:

**萃取要盡早,最好在機上。** 如果任務的產出是「找出有缺陷的絕緣礙子」,那麼在機上跑推論、只上傳有疑慮的影像與座標,可以把資料量砍掉一到兩個數量級。這是[資料重力判準](../00-system-overview/02-system-boundaries.md)最有經濟價值的應用。

**保留政策要在資料進來之前決定。** 「先存著,以後再說」的結果是永遠不敢刪——因為沒人記得哪些能刪。每一類資料在建立時就帶上保留期限與刪除規則。

**飛行紀錄跟影像的政策不同。** ULog 很小(50 MB 級)但價值高且法規可能要求保存;影像很大但多數沒有長期價值。不要用同一套政策處理。

**要能回答「這張照片是哪次任務、哪台機、什麼時間、什麼姿態下拍的」。** 沒有這組中繼資料,影像就只是檔案,無法用於任何分析。中繼資料要跟檔案一起產生,不要事後補。

## 3. 機隊的狀態模型

除了任務,機隊本身也有狀態要管:

| 實體 | 關鍵欄位 |
|---|---|
| 機 | 序號、型號、韌體與軟體版本、累積飛行時數、維護狀態、目前位置與可用性 |
| 電池 | 序號、循環次數、健康度、目前所在的機、充放電歷史 |
| 酬載 | 序號、型號、校正狀態、目前掛在哪台 |
| 起降場 | 位置、容量、充電能力、天候感測 |
| 操作者 | 身分、證照與效期、可操作的機型與空域 |

**電池要單獨管理**,而不是當成機器的一個屬性。它是消耗品、會在機器之間流動、有獨立的健康度曲線,而且是最常見的事故原因之一。追蹤循環次數與衰退率,可以在它變成飛行風險之前換掉。

「這台機現在能不能飛」這個問題,答案是上面所有實體的交集:機器本身可用、有健康的電池、酬載已校正、操作者有證照、空域允許。把它做成一個明確的可飛性檢查,比讓調度員自己記住這些條件可靠得多。

---

## 4. 空域與合規的架構接點

不同國家的規則差異大且更新頻繁,但**系統要處理的東西是共通的**:

| 需求 | 系統要做什麼 |
|---|---|
| 識別 | 每台機有法規認可的識別碼,並能廣播 / 上報 |
| 位置上報 | 依規定的頻率與格式送出即時位置 |
| 空域授權 | 飛行前取得許可,飛行中維持在授權範圍 |
| 衝突資訊 | 取得附近其他航空器的資訊 |
| 紀錄保存 | 飛行紀錄與批准紀錄保存指定年限 |

架構上的處理原則:

**把法規邏輯集中在一個模組,不要散在各處。** 規則會改,而且不同國家不同。集中之後,進新市場只要換一組規則實作。

**授權狀態要進可飛性檢查。** 沒有取得空域許可就不該派工,這件事應該由系統擋住,而不是靠流程提醒。

**上報是即時路徑,不能靠事後批次。** 網路式的位置上報有頻率要求,漏報是合規問題。

開源可用的元件:[opendroneid-core-c](https://github.com/opendroneid/opendroneid-core-c) 處理廣播式識別的編碼,[InterUSS DSS](https://github.com/interuss/dss) 是空域探索與同步的標準實作(Linux Foundation 專案)。**這些是標準的實作而非某家公司的產品**,接上去比自己重做合理。

實際的法規條文以主管機關現行規定為準,本文只講架構影響。

## 5. SaaS 還是私有化部署

這個決定會影響整個系統設計,而且通常由客戶的產業決定,不是由技術決定。

| | SaaS | 私有化 |
|---|---|---|
| 適合 | 一般商業巡檢、測繪、農業 | 政府、國防、關鍵基礎設施、資料不得出境的產業 |
| 更新 | 你控制節奏 | 客戶控制,版本會分歧 |
| 資料 | 集中,可跨客戶做分析 | 各自獨立 |
| 除錯 | 可直接觀察 | 只能靠客戶提供的紀錄 |
| 成本結構 | 你付基礎設施 | 客戶付,但支援成本高 |

如果兩者都要支援(很常見),從第一天就要:

- **把跟雲端服務綁定的東西抽象掉。** 直接用某家雲的專有服務,私有化時要重寫。
- **設計成單一部署單元。** 私有化的環境通常沒有 Kubernetes 專家,能用一份 compose 檔跑起來的東西存活率高很多。
- **版本要能分歧。** 客戶環境會停在舊版好幾年,協定與資料格式的相容性要當成長期承諾。
- **可觀測性要能離線收集。** 客戶不會給你連線權限,要能請他們匯出一包診斷資料。

---

## 6. 跟既有系統整合

機隊平台很少是孤島。常見的整合對象與整合點:

| 對象 | 整合點 |
|---|---|
| 工單 / 維護系統 | 任務由工單觸發,結果回寫工單 |
| ERP / 資產管理 | 機、電池、酬載當成資產;成本歸屬 |
| 資產台帳(電網、管線、建物) | 任務目標對應到實體資產的編號 |
| 地理資訊系統 | 成果進入既有的圖層體系 |
| 影像分析 / AI 平台 | 成果送去分析,結果回來 |

整合的關鍵是**識別碼的對應**:你的「目標點 #47」跟客戶系統裡的「電桿 TP-2024-0031」必須有一張明確的對照。這件事看起來瑣碎,但它是整合能不能成立的核心——沒有穩定的識別碼對應,所有分析結果都無法回饋到客戶的既有流程裡。

---

## 7. 這一章的結論

1. 一趟 30 分鐘的巡檢約產生 15.7 GB;十台機每天五趟就是 785 GB/天、287 TB/年。這個數字決定架構。
2. 資料要分層(熱 / 溫 / 冷 / 永久),保留政策要在資料進來前決定,飛行紀錄與影像用不同政策。
3. 萃取盡量在機上做,可以把上傳量砍掉一到兩個數量級。
4. 電池要當成獨立實體管理,它會在機器之間流動且有獨立的衰退曲線。
5. 法規邏輯集中成一個模組,授權狀態要進可飛性檢查。
6. SaaS 與私有化都要支援的話,避開雲端專有服務、能用一份 compose 跑起來、接受版本分歧。
7. 系統整合的核心是識別碼對應,沒有它成果無法回饋到客戶既有流程。
